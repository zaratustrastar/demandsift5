# T03 — unresolved AI work is not negative relevance

Implemented and verified locally August 31, 2026. Phase 1's instrumentation and quality safeguards are complete. Production remains untouched; live quality/latency benchmarks have not run.

## Changes

- `TriageProcessingOutcome` separates pending/succeeded/unresolved processing from semantic judgments. Unresolved records carry only a safe error code, recoverability and logical-submission attempt count. HTTP attempts remain separately observable through T01.
- `triageConversations` returns actual judgments only. Its tolerant mode drains independent work and returns explicit incomplete coverage; it no longer synthesizes negative decisions. Strict callers still receive errors. In-flight siblings settle before an error returns, preventing their callbacks from racing a subsequent invocation.
- Valid partial-batch judgments checkpoint immediately even if other IDs in that batch later exhaust recovery. Bisection, model settings, batch size, concurrency and retry ceilings remain unchanged.
- Resume validates checkpoint shape and identity and recognizes the exact legacy synthetic-failure signature. Genuine negative judgments remain valid; only missing/unresolved/invalidated IDs are submitted again.
- The workflow persists processing and coverage independently. Claimed success without a validated judgment cannot satisfy coverage. An exhausted incomplete triage run is `failed` with saved profile/discovery/successful judgments and a `triage_coverage_incomplete` code, never a false exhaustive zero. That code is terminal in both the application and worker because the provider's bounded recovery already ran. Ordinary transient provider failures keep their existing bounded job recovery.
- Internal partial work is preserved for later T14/T16 presentation; this ticket does not yet display it as a user-facing partial report.

## Verification

Nine new tests cover exact legacy recognition, ordinary negative reuse, missing-ID-only recovery, valid partial-batch checkpoints, safe refusal outcomes, in-flight sibling draining, persistence-collector failure, dishonest success metadata, and actual workflow failure/resume using the real AI provider with stubbed requests.

The key integration test resolves 25 of 26 records, preserves those 25 judgments, marks the remaining record unresolved and the scan failed, then resumes by requesting **only that remaining ID**. Deep review is not entered until coverage is complete.

- Focused provider/workflow/replay group: **96 passed**.
- Full suite: **555 total, 553 passed, 1 failed, 1 skipped**. The only failure remains the T00 stale landing-page heading assertion; the skip is the live Apify probe.
- Build, TypeScript no-emit, lint and whitespace checks pass; same three pre-existing font warnings.
- Two older tests explicitly expecting fabricated negatives were deliberately rewritten to assert separate unresolved outcomes and incomplete coverage instead. No source snapshots were silently accepted as regressions.

## Operations and limits

Optional fields live in existing scan JSON; no database migration or new external service. Prior checkpoint: `checkpoint/t02-review-depth`. Reverting to code that manufactures negative judgments is not a quality-preserving rollback; retain the development history and do not deploy a mixed release.

Logical submission counts are not billable-request counts. A timeout may still incur provider cost. Best-effort checkpoint callbacks retain the current repository contract; T05 still needs database execution fencing and serialized writes.
