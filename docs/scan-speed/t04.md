# T04 — reuse the approved website evidence

Implemented and verified locally August 31, 2026. Production is unchanged.

## Change

A scan-local, integrity-checked website snapshot now separates successful crawling from AI analysis. The snapshot is saved before the AI call and reused on analysis retry, scan resume and after profile approval. It preserves the existing content-derived source IDs and the protected crawler's maximum of four pages. Reported page counts reflect successful pages, not the configured limit. Context-only input never crawls.

The profile binds to its exact snapshot. Missing, corrupt, differently scoped or mismatched evidence fails safely; it is not silently replaced underneath an approved profile. Legacy website profiles may bind after a protected crawl only if all profile and business citations match the newly read evidence. Changed legacy evidence requires a new scan and review. No cross-scan freshness cache or security bypass is introduced.

Files: `website-snapshot.ts`, `scan-workflow.ts`, additive scan contracts and terminal-error classification. Raw crawl data stays internal and uses existing scan JSON storage; the status API must not expose it.

## Verification

Twelve new tests exercise integrity/scope, unchanged citations and profile, analysis retries, failure/restart recovery, persistence failure before AI, real page count, context input, matching and changed legacy evidence, and tampered approved snapshots. The crawler security/concurrency and competitor suites also pass.

- Focused website/security/competitor group: **39 passed**.
- Full suite: **567 total, 565 passed, 1 failed, 1 skipped**. The failure remains the pre-existing obsolete landing-page heading assertion; the skip is the paid live Apify probe.
- Production build, TypeScript, lint and whitespace checks pass. Lint retains three pre-existing font warnings.

## Expected benefit and limits

One successful website crawl per new scan instead of repeated crawling during AI retries or approval-to-run transitions. Savings equal the eliminated crawl duration, not the whole website-analysis stage. The observed 34-second website stage mixes crawl and AI time, so it is not a defensible 34-second saving. No paid latency benchmark has run.

Checkpoint predecessor: `checkpoint/t03-triage-coverage`. Additive data requires no migration. T05 follows with database ownership fencing and immutable checkpoint writes before scheduling changes.
