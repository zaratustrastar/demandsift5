# T05 — database ownership and immutable checkpoints

Implemented and verified locally August 31, 2026. No production changes or paid requests.

## Guarantees

- Worker requests carry their claimed attempt. Lease refresh, completion and failure require both worker ID and attempt, including when a worker ID is reused.
- Each executor acquires a random token in the scan's durable record. PostgreSQL locks the claimed job then scan, verifies workspace/attempt/worker, and conditions checkpoint updates on the execution token. A new job claim invalidates the old executor even before the new executor starts. A second web process on the same attempt waits for the separate executor lease to expire; it cannot displace healthy work just by polling.
- Executor heartbeats run every 15 seconds with a 90-second recovery lease. Heartbeat writes update only the internal heartbeat, not the scan's last-work timestamp. Lost ownership or an unavailable ownership check aborts local HTTP work and prevents further provider requests. Existing request timeouts/cancellation are combined with that signal, including the direct AI fallback and the protected website crawler.
- Successful checkpoints remain immediate. The existing per-scan write queue now captures immutable snapshots at enqueue time. Shared workflow callbacks accumulate their changes before enqueueing. Non-executor updates use a revision check; stale edits conflict instead of overwriting newer data. Completion releases execution ownership; later executor saves cannot regress it.
- Pipeline-created replies are fenced in the same database transaction as their ownership check. Known Harshmaur run IDs, dataset IDs and hashed inputs checkpoint before polling; credentials and search text are not included in that ledger. T11 still needs run reconciliation rather than claiming exactly-once external billing.

## Verification

A temporary loopback-only PostgreSQL **16.15** instance was built from the official source archive and checksum-verified outside the repository. The integration suite uses real repository methods, the actual production worker's SQL, a separate ORM connection (as in production), relevant migration DDL, and a randomly named disposable schema. It never uses `DATABASE_URL` or connects to a non-loopback host. It removes only its own test schema.

Eight PostgreSQL tests cover competing job claims, both claim implementations, worker-ID reuse, stale scan/reply/job/heartbeat writes, same-attempt web restart, concurrent checkpoints, terminal-state protection and stale user edits. Six runtime tests cover exact owner identity, cancellation, no new requests after loss, failed ownership checks, idle heartbeat loss, and saving known Apify identity before polling. A new serialization test proves queued snapshots do not change when the reducer changes later.

- Full suite with the PostgreSQL tests enabled: **582 total, 580 passed, 1 failed, 1 skipped**. Only the known obsolete landing-heading assertion fails; the paid Apify probe is skipped.
- Production build, TypeScript, lint and whitespace checks pass; three existing font warnings remain.
- Source-shape assertions were adjusted for explicit ownership/cancellation plumbing; their crawler depth/security and queue invariants remain intact.

## Rollout/recovery notes

No schema migration or external queue is needed; ownership/revision are additive JSON fields. **Deploy worker and web together and drain/stop old executors first.** The worker's internal protocol now requires an attempt number. An old binary that does not enforce fencing must not coexist with new executors. The 90-second lease is recovery delay, not a promised scan-time improvement.

Progress-write coalescing is deferred until there is a distinct progress-only stream; expensive work is not delayed behind a timer. Existing secondary monitoring/visibility workflows are unchanged; generic worker job mutations are attempt-fenced, while scan-record fencing is implemented for the DemandSift scan pipeline. DB unavailability fails closed locally; an already accepted external request can still be billed. No exactly-once claim is made.
