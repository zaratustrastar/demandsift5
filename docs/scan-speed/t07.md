# T07 — compact, truthful progress

Implemented locally August 31, 2026. No production changes or paid calls.

## Contract and implementation

- `lib/domain/scan-progress.ts` defines version 1 of the bounded public read model. `lib/server/scan-progress.ts` maintains it beside existing stage fields. It includes distinct analysis/run timestamps, heartbeat versus real-work timestamps, query states, canonical eligible records, successful/unresolved triage, selected/completed deep reviews, actually verified threads, insight state and ready-result counts. Unknown old-scan values are `null`, not invented zeros. There is no estimated completion time or equal-weight percent.
- `scan-workflow.ts` updates counts from sets/maps and final coverage, not callback/attempt increments. The selected deep-review count remains separate from actual thread fetching; mock evidence does not claim public threads were fetched. Query and triage stages may both be active in the contract; T10 will introduce execution overlap.
- Harshmaur reports unique query states across its bounded worker pool and retries. Completed zero-result searches count as successful searches. Resume skips only covered queries, retains successful candidates, and reports cumulative coverage. The old all-remaining-chunks-failed return now retains evidence **and marks missing coverage**. Complete recovery clears prior degradation. The existing single-remaining-query exception still propagates for job-level retry.
- `StateRepository.getScanStatus(scanId, workspaceId)` uses a JSONB allow-list projection inside PostgreSQL. It does not load the crawl, complete profile, provider ledger, judgments or full report into the web process. Ownership is part of the query. The status route includes access information, keeps `report: null`, and sends `Cache-Control: private, no-store`. Full report/restoration routes remain available.

## Verification

- Real PostgreSQL integration: multi-megabyte synthetic evidence/report fields produce a status object under 3 KB; sentinel content and internal execution IDs are absent. Another workspace and a missing scan return no status. A fresh heartbeat does not advance the saved last-work timestamp.
- Real workflow with IO fixtures: repeated batch callbacks count 12 unique successes once, preserve the eight-review target, and never claim review completion on model failure.
- Provider replay: concurrent queries, a retry without double counting, all remaining chunks failing, recovery without re-fetching covered searches, and no new actor after complete coverage. Existing provider tests now assert corrected coverage diagnostics rather than reference identity or an absent boolean.
- Built API checks analysis/run milestones, context privacy, compact responses, thread-fetch honesty and cross-workspace denial.
- Full suite: **597 total, 595 pass, 1 known obsolete landing-heading failure, 1 skipped paid probe**. Production build, TypeScript, lint and whitespace checks pass; three existing font warnings remain.

This reduces status-transfer/application decoding overhead; it is not a measured reduction in provider scan time. PostgreSQL still reads JSONB internally; a separate progress table is not justified without evidence of database pressure. Discovery can still finish with explicitly limited coverage under existing multi-query failure behavior; T10/T11 address reconciliation/recovery. No quality budgets, prompts, candidate limits or provider concurrency were reduced.
