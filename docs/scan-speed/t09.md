# T09 — bounded, cancellable AI dispatch

Implemented locally August 31, 2026. Production and provider accounts are unchanged.

`lib/ai/bounded-dispatcher.ts` supplies a FIFO request gate and an incremental batch dispatcher with submit/flush/drain/cancel. The gate is held through response-body consumption and released before retry backoff. Ordinary batch failure stops queued dispatch but drains successful siblings; explicit cancellation aborts transport and backoff and prevents further dispatch.

`lib/providers/openai.server.ts` retains 25-item batches, four workers, original input order, prompts, models, output allowance, retry budgets, fallback routing and coverage semantics. Its scheduler now uses the shared dispatcher. Recursive length splits and direct fallback receive the primary provider's same HTTP gate, so they cannot multiply the four-request limit. `scan-workflow.ts` passes the owned execution's cancellation signal.

`lib/ai/triage-dispatcher.ts` exposes one incremental dispatcher per scan for T10. Immutable candidate snapshots and SHA-256 versions include the full candidate, full business context, models, and an explicit input/prompt revision. Object key order is canonical; array order, author, metrics, timestamps, lanes, queries and provenance are preserved. Callbacks carry the exact input versions; duplicate versions are not submitted again. Different versions of one external ID cannot share a batch. Clocks and provider I/O remain injectable.

This is a safety prerequisite, not a measured speed improvement. It does not yet overlap discovery/triage or impose an account-wide limit across processes; those are T10/T17. A concurrency limit is not a tokens-per-minute limit. Retry policy itself remains T11; current guidance recommends bounded retries and warns that failed requests also consume limits ([OpenAI rate-limit guide](https://developers.openai.com/api/docs/guides/rate-limits)).
