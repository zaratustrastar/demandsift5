# T11 — coordinated provider recovery

Implemented September 1, 2026 in the isolated speed-up branch. Production remains unchanged.

## Outcome

AI and Apify recovery now have durable, bounded ownership-aware behavior instead of independent nested retry loops. The change is intended to reduce long-tail scans and prevent duplicate paid work. It does not reduce search depth, triage coverage, qualification depth, prompts, models, or result-selection rules.

The AI behavior is behind `SCAN_COORDINATED_RETRIES=1`; it remains off until the staged quality and latency gate. The Apify run ledger is enabled in scan execution because it is a recovery/cost correctness control rather than a tuning change.

## AI recovery

- `lib/ai/recovery-budget.ts` owns a single per-scan request/deadline ledger keyed by an exact hash of the provider route and complete request input.
- A request is reserved and persisted before the HTTP call. An ambiguous response therefore consumes budget and is never treated as a free retry.
- `Retry-After` is accepted as seconds or an HTTP date, persisted, and treated as a minimum delay. Otherwise recovery uses bounded exponential backoff with jitter.
- Authentication, quota, and invalid-request failures are terminal. Missing coverage, malformed structured output, oversized output splitting, gateway recovery, and the existing direct fallback share the same budget.
- The configured Surplus route remains primary. The existing direct OpenAI fallback is used earlier only for eligible gateway failures, without racing duplicate requests.
- Execution ownership cancellation reaches queued and active provider calls and prevents new calls from being scheduled.

Effective defaults are 20 HTTP requests per exact input and a 15-minute recovery deadline. Environment validation clamps request limits to 3–60 and deadlines to 30 seconds–30 minutes. These are safety ceilings, not an assertion that calls should normally approach them.

## Apify recovery

- `lib/providers/apify-run-recovery.ts` persists a start intent before the non-idempotent actor-start request, then persists the accepted run and dataset IDs immediately.
- A lost/ambiguous actor-start response fails closed with `apify_start_ambiguous`; a job retry does not blindly start another paid actor because the API does not expose a caller idempotency key for this operation.
- Accepted runs are inspected and resumed after interruption. Dataset pagination resumes from the known dataset and keeps already returned records.
- Only a confirmed terminal failure or confirmed abort permits a replacement start. A missing abort response is not proof of an abort.
- Throttled start requests use the persisted `Retry-After`. Total starts are capped at three for one exact actor input across job attempts rather than three on every attempt.
- Execution ownership loss cancels local polling without aborting a valid remote run; the next owner resumes it.
- The existing one-time Trudax mapping recovery is represented as a separate, explicit purpose. Concurrent identical requests within one scan share one in-flight operation.

This follows the official Apify lifecycle: an asynchronous actor start returns a run object with its dataset ID, a run can be inspected with bounded `waitForFinish`, and abort is valid only for starting/running work. See the [Run Actor](https://docs.apify.com/api/v2/actors-runs-post), [Get Run](https://docs.apify.com/api/v2/actor-run-get), and [Abort Run](https://docs.apify.com/api/v2/actor-run-abort-post) API references. The AI backoff classification follows the [OpenAI rate-limit guide](https://developers.openai.com/api/docs/guides/rate-limits).

## Other corrections

- The documented background executor timeout now matches the existing runtime minimum of 1,200 seconds.
- Provider error codes are preserved through workflow and worker boundaries so authentication, quota, ambiguous start, and exhausted recovery failures remain diagnosable.
- Nonrecoverable discovery/enrichment errors no longer degrade into fabricated successful empty or discovery-only results.
- Five provider tests that compiled hand-picked source fragments now use the shared TypeScript test loader, ensuring recovery imports and behavior are exercised.

## Expected effect and limits

No latency percentage is claimed without provider-backed benchmarks. This ticket removes multiplicative retry tails and prevents ordinary job recovery from repeating known paid Apify work. A truly ambiguous actor-start response cannot be safely reconciled through the current Apify API, so it is retained as an explicit partial failure rather than guessed successful or automatically duplicated.

Rollback for the AI behavior is `SCAN_COORDINATED_RETRIES=0`. The Apify helper can be reverted at this checkpoint, but doing so restores duplicate-start risk after interruption.
