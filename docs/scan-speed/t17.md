# T17 handoff — queue capacity without provider overload

## Outcome

DemandSift can now run two queue executor lanes without doubling provider load. The second lane remains disabled by default and cannot be enabled unless PostgreSQL-backed global provider caps are enabled.

Queue selection now gives fresh user-started analysis/full-scan jobs precedence over fresh scheduled monitoring jobs. With two lanes, one lane accepts only interactive scan work, while the second accepts all supported job types. Scheduled jobs gain one priority level per configured aging interval and eventually outrank fresh interactive work, so they cannot starve. Stale running jobs are reclaimed first. Within the same priority, workspaces with fewer active jobs are preferred.

## Shared capacity

Migration `0011_provider_capacity_leases.sql` adds expiring waiters and fenced leases for two independent pools:

- `ai-request`: held only around a provider HTTP request through response-body consumption. Retry backoff does not hold a permit.
- `apify-actor`: held for the whole Actor lifecycle. Short start/status/dataset HTTP calls do not consume separate Actor permits.

Permit acquisition is serialized per pool with a PostgreSQL transaction advisory lock. Selection prefers the workspace with the fewest live permits, then FIFO. Lease release requires the current random lease token; a crashed/old process cannot free a successor's permit. Expired leases and abandoned waiters are reclaimed during acquisition.

The primary scan's existing Apify ledger remains authoritative. A saved Actor ID is reconciled before replacement work. Confirmed terminal or rejected starts release immediately; running or ambiguous starts retain capacity until the lease expires. The daily Reddit monitor and AI visibility sidecar use the same Actor pool. Scan, competitor, reply, candidate-reply, visibility, and acceptance-diagnostic AI calls use the same AI pool.

## Configuration and rollout

Safe defaults preserve the current single-executor behavior:

```dotenv
PROVIDER_GLOBAL_CAPS=0
AI_GLOBAL_REQUEST_CONCURRENCY=4
APIFY_GLOBAL_ACTOR_CONCURRENCY=9
PROVIDER_CAPACITY_POLL_MS=250
AI_REQUEST_LEASE_SECONDS=360
BACKGROUND_WORKER_CONCURRENCY=1
BACKGROUND_WORKER_ROLE=combined
BACKGROUND_JOB_AGING_SECONDS=300
```

`BACKGROUND_WORKER_CONCURRENCY=2` fails startup unless `PROVIDER_GLOBAL_CAPS=1`. The supported roles are `combined`, `executor`, and `scheduler`; roles allow a future scaled deployment to nominate scheduler-only and executor-only instances. Existing scheduler transactions and dedupe keys remain the second line of defense against duplicate scheduled jobs.

Rollout order: apply migration; deploy with defaults; enable provider caps while retaining one lane; observe permits/rate limits; then enable two lanes. Rollback first returns concurrency to one after active jobs drain, then disables global caps. The additive capacity tables can remain.

## Remaining external gate

No production concurrency or provider cap is enabled by this ticket. Provider/account limits must be confirmed in staging, and two lanes should be enabled only after observing real 429/retry/cost behavior. This ticket reduces queue delay under contention; it does not reduce an idle scan's provider execution time.
